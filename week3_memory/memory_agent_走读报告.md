# memory_agent.py 代码走读报告

> 对象：`memory_agent.py`（Week 3：分层记忆 + Memory Read/Write）
> 依据：一次完整运行（会话A踩坑 → consolidate 沉淀 → forget 衰减 → 会话B冷启动复用，纠错轮数 1→0）

## 全景：记忆是 Agent 的"第四个组件"

三周的累积视角：Week 1 造了**工具循环**（Agent 如何行动），Week 2 造了**编排**（行动如何不失控），Week 3 造**生命周期**（经验如何跨运行存活）。本周文件的数据流：

```
会话A 运行 ──► trace（工作记忆）
                 │
                 ▼
          MemorySystem.consolidate()     写：LLM 从轨迹提取经验
                 │
        ┌────────┴────────┐
        ▼                 ▼
  VectorMemory        GraphMemory        长期记忆（向量 + 图）
        │                 │
        └────────┬────────┘
                 ▼
          MemorySystem.read()           读：按问题相似度取回
                 │
                 ▼
        system prompt 尾部追加记忆块 ──► 会话B 冷启动即受益
```

**记忆不在循环里，在循环外**——`run_task()` 的循环逻辑对记忆零感知，这是本周最重要的架构决定（第 6 站细讲）。

## 第 1 站：三层记忆的判别标准（`memory_agent.py:75-148`）

三层的划分依据不是"存什么"，而是**生命周期和载体**：

| 层 | 类 | 生命周期 | 载体 | 运行中的体现 |
|---|---|---|---|---|
| 工作记忆 | 无（就是局部变量） | 单任务 | `trace` + `messages`（232、238 行） | 本次任务的 Action/Observation 流 |
| 短期记忆 | `ShortTermMemory` | 单会话 | 按 `session_id` 的 dict（79 行） | 会话内多任务共享的对话历史 |
| 长期记忆 | `VectorMemory` + `GraphMemory` | 永久（直到遗忘） | 嵌入向量 / 三元组 | 跨会话的经验与事实 |

两个设计细节：

- **工作记忆根本没有类**——它就是 `run_task` 里的局部变量，任务结束自然消失。不为它建抽象是对的：它已经是 Python 原生的东西（局部作用域）。
- **短期与长期的边界在 `drop()`**（87-88 行）：会话结束，短期记忆整体丢弃，**除非** consolidate 先把有价值的部分沉淀进长期。这个"除非"就是人类记忆里"睡眠巩固"的机制——清醒时积累（短期），睡眠时筛选固化（consolidate），醒来后只带走结构化的东西（长期）。

## 第 2 站：`embed` / `cosine`——向量检索的机制核心（`memory_agent.py:56-68`）

```python
def embed(text, dim=128):
    vec = [0.0] * dim
    for ch in ...:      vec[hash(ch) % dim] += 1.0              # 单字符 → 桶
    for i in range(...): vec[hash(text[i:i+2]) % dim] += 1.0    # bigram → 桶
    norm = math.sqrt(...)
    return [v / norm for v in vec]                              # L2 归一化
```

四步机制，每步都有生产对应物：

1. **分词**：字符 bigram（对中文友好）；生产是 tokenizer；
2. **映射到固定维度**：`hash % dim` 把任意文本压进 128 维——嵌入的本质：**变长文本 → 定长向量**；
3. **归一化**：除以模长，向量落在单位球面——此后**余弦相似度 = 点积**（`cosine` 就是裸点积）；
4. **桶碰撞**：128 维装不下所有 bigram，不同 gram 落同桶——toy 版的精度损失来源。

诚实边界（文件头 23-25 行已声明）：这是**词法相似**（字面共享越多越近），不是语义相似。运行中"查询城市天气"以 0.44 相关度命中拼音经验，靠的是记忆文本里有"城市/天气"字面。换真 embedding 只改函数体——**检索机制（余弦+top-k）一行不动**。

## 第 3 站：`VectorMemory`——记忆条目的元数据设计（`memory_agent.py:95-128`）

```python
@dataclass
class MemoryEntry:
    text: str                # 内容本身
    kind: str                # episodic(经验) / semantic(事实) —— 检索时可过滤
    importance: float = 1.0  # 遗忘的输入
    ts: float                # 创建时间 —— 衰减的输入
    vec: list[float]         # 写入时算好（不是检索时）—— 一次嵌入，多次复用
```

`write` 里 `vec=embed(text)`（109 行）：**嵌入在写入时算一次并存储**，检索时只算 query 的。生产中 embedding 调用要花钱，这个时机选择直接决定成本模型。

`retrieve` 是全量扫描 + 排序（111-116 行）——O(n) 在演示里无所谓，生产对应物是 ANN 索引（pgvector 的 ivfflat/hnsw）。**机制不变，规模变了**。

## 第 4 站：`decay_and_forget`——遗忘的数学（`memory_agent.py:118-128`）

```python
age_days = (now - e.ts) / 86400.0
e.importance *= 0.5 ** (age_days / HALF_LIFE_DAYS)   # 指数衰减
if e.importance < FORGET_THRESHOLD:  删除
```

指数衰减是**无干预情况下的默认命运**：一条记忆 15 天没人用，重要性减半；40 天后 0.2 的低价值记忆衰减到 0.079 < 0.1，被删。运行中"运行耗时 3.2 秒"被遗忘、拼音经验保留——但后者只是因为才刚出生。**当前实现只有时间衰减，没有"使用即强化"**：拼音经验 40 天不被检索也会被同样遗忘。补上"命中即提升 importance"（人类记忆的"越用越牢"）是课后练习。

细节：122 行 `for e in self.entries[:]` 切片拷贝再遍历，否则循环内 `remove` 会跳元素。

## 第 5 站：`GraphMemory` 与"向量/图分工"（`memory_agent.py:135-148`）

两类长期记忆回答**不同的问题**：

| | VectorMemory | GraphMemory |
|---|---|---|
| 回答 | "**哪条**经验与当前任务相关？"（排名） | "关于**这个实体**的确定事实是什么？"（枚举） |
| 检索方式 | 相似度（模糊、有分值） | 实体匹配（精确、无分值） |
| 擅长 | 经验教训（自然语言） | 结构化事实（可多跳推理） |
| 生产对应 | pgvector | Neo4j |

图的真正威力在多跳推理（`(A)-[:同款工具]->(B)` 推出 A 的参数格式），本实现的 `query` 只做单实体过滤——刻意裁剪：演示"分工"，不演示图查询语言。

**运行中暴露的缺陷**：`read()` 的图检索靠"问题文本包含工具名"（170-171 行），会话 B 的问题"上海和广州…跑步"不含 `get_weather` 字面 → 图记忆整段没被注入（运行输出的"注入的记忆块"里没有图记忆段可证）。修法：先用向量检索定位相关工具、再用工具名查图（两跳），或先抽实体。这暴露了 Agentic RAG 的通用课题：**检索入口的召回率决定整个记忆系统的上限**。

## 第 6 站：`run_task`——记忆与循环的解耦（`memory_agent.py:220-260`）

记忆的**三个注入点**全部在循环之外或循环入口：

```python
if memory_block:
    system += f"\n\n{memory_block}"        # ① 长期记忆 → system 尾部（229-230）
messages = stm.history(session_id)          # ② 短期记忆 → 会话历史（232）
trace = []                                  # ③ 工作记忆 → 任务轨迹（238）
for step in ...:                            # 循环体对记忆系统零感知
```

对比反模式：把"查记忆"放进循环里每步都查——每步都花检索成本、注入内容可能漂移（模型中途换记忆依据）。**记忆按任务粒度注入，不按步注入**——上下文稳定，也利于 prompt cache。

注入位置的讲究：记忆块加在 **system 尾部**而非 messages。三个原因：system 每轮请求都完整在场（放 messages 里会随对话滚远）；语义上是"背景知识"而非"对话内容"；生产中可单独给它打 `cache_control`。

## 第 7 站：`consolidate`——记忆写入口的两个契约（`memory_agent.py:179-205`）

**Prompt 契约**（180-185 行）两句关键指令，直接决定检索质量：

- "写成自包含的短句，**包含触发场景**"——"调用 get_weather 查询城市天气时，city 参数应使用小写拼音"优于"city 参数用拼音"。触发场景词（天气/城市）正是日后检索时与问题重叠的词——**写记忆就是在为未来的检索埋钩子**；
- "忽略仅对本次问题成立的细节"——防"北京今天 26°C"这类过期数据入库（天气明天就变，拼音格式永远不变——**事实的半衰期**天然不同）。

**解析契约**（194-200 行）：`re.search(r"\{.*\}")` 剥围栏再 `json.loads`。本周调试真踩过的坑（第一次运行 consolidate 因代码围栏解析失败而空转，会话 B 白多踩一次坑）——Week 1 的"LLM 输出必须容错解析"在记忆写入口的复现。**记忆管道上任何一环解析失败，损失是双倍的**：本次没沉淀 + 未来每次运行重新踩坑。

（小瑕疵：201 行 `for m in ...` 复用了 195 行的正则变量名 `m`，能跑但遮蔽变量。）

## 已知缺陷清单（按危害排序）

1. **记忆污染无防线**：consolidate 提取的经验未经验证就入库。第一版运行时它差点沉淀"get_weather 报错信息不可信"这条**错误结论**（真相是参数格式问题）。错误经验会被每次 `read()` 放大。生产需要：入库前重放验证、置信度字段、人工审核通道。
2. **图记忆注入条件太窄**（第 5 站已析）：问题不含工具名字面 → 图记忆静默缺席。
3. **无使用反馈**：被 `retrieve` 命中应提升 `importance`（对抗衰减）——"越用越牢"。
4. **短期记忆无治理**：`ShortTermMemory` 的 messages 无限增长，没接 Week 2 的 `compress`——跨周知识未缝合，留作练习。
5. **embed 词法级**（已声明）：语义泛化（"气象"↔"天气"）不可得。

## 自测问题

> `retrieve` 返回 top-k 时带着相关度分值（0.44），为什么 `read()` 只是把分值打印出来，而不是用它过滤掉低相关的记忆？

**答案**：这里 k=2 且记忆库极小，0.44 已是 top-1，打印分值是为了**可观测**（能看到检索质量）。但生产里必须有阈值：注入 10 条 0.2 相关度的垃圾记忆比不注入更糟——每条记忆消耗 token、稀释注意力、诱导模型套用不相关经验（记忆污染的检索侧入口）。正确姿势是 `score < MIN_RELEVANCE 丢弃 + 命中数不足时不注入`，让"没有相关记忆"成为合法输出。这也是 RAG 的经典调参点：**召回率 vs 精确率的权衡发生在注入阈值上**。

## 与 Agentic RAG 的关系

`read()` 就是 RAG 的 Retrieval（按问题检索、注入上下文），`consolidate()` 是普通 RAG 没有的部分——**语料库自增长**：Agent 用出来的经验反哺知识库，检索质量随使用提升。这就是"Agentic RAG"区别于静态 RAG 的那一半。学习计划中"向量记忆 + 图记忆"的混合检索（hybrid search）也正是本文件 `read()` 的两路合流。
